第三章

设计策略

因"问"制宜的回答策略

宽泛问题要简练高效，具体问题要好奇和启发。不同类型的对话需要不同的交互密度和信息结构。

设计策略三角

📖 阅读效率

度量：用户满意度
目标：信息一目了然，减少认知负担

🖱️ 互动意愿

度量：点击率 / 对话轮数
目标：激发探索欲，引导深入对话

🤝 信任感

度量：留存 / 满意度
目标：让用户相信AI的输出是可靠的

谁来控制表达

Product Controls vs Model Controls

Product Controls：开发者定义规则（只能用某几种卡片），产品规定结构，模型只填数据。

Model Controls：模型自己决定呈现方式（表格、Grouping、完整HTML），产品只负责渲染。

现实定位：大多数产品处于中间地带 — 由应用设定边界，模型在边界内自适应。Copilot目前处于Medium Freedom，正在向High Freedom演进。

根据模型能力动态调整自由度

模型能力越强，可以给予的表达自由度越高。设计系统需要能够根据底层模型的能力动态调整GenUI的自由度级别 — 这不是一次性选择，而是持续演进。

AI Workflow 工具 — 解决GenUI测试难题

我一直希望让Copilot能输出内容丰富的UI界面，而不只是text heavy的大段文案。在古法设计时期，用Figma手搓很难穷尽所有组合场景。

经过调研，我找到一个开源的GenUI库，并理出了实现的技术架构：

  • 定义一个GenUI design system
  • 和LLM约定返回内容中带有表达GenUI的Tag
  • Agent根据规则，将带Tag的返回信息渲染成带有UI的回复内容

我把开源库clone到本地，将GenUI样式调整得尽可能和Copilot相似，然后和Copilot代码库结合。

[GenUI效果对比 — 日本旅游计划：纯文本 vs GenUI]
对比纯文本的AI回答，GenUI内容结构明显更有重点，视觉上更有吸引力。甚至输入信用卡相关问题，AI直接生成了可交互的申请流程。
[可交互的信用卡申请流程 GenUI]

至此，增加新的GenUI组件不再需要Figma手搓，只需向Claude Code描述新的components和规则，甚至让AI自动生成evals测试，就能快速判断设计表现是否符合预期。

2B场景：GenUX

企业用户使用Copilot时，数据在Teams、Outlook、Office等产品中流动，体验横跨多个场景。对话中的GenUI不能只是简单交互的组件，而是整个Workflow — 用户要能用对话完成工作中的任务，所以我们把它叫做GenUX。

用户与模型的交互模式

📋

Queue

排队式请求，用户提交后等待

🎯

Steer

引导式交互，用户实时调整方向

⚡

Interrupt

中断式操作，用户随时介入

反思

  • GenUI的自由度需要与模型能力匹配 — 过高的自由度在模型不成熟时会带来不可控的体验
  • 组件化设计系统是GenUI规模化的基础
  • AI辅助的设计工具（Claude Code + 开源GenUI库）大幅提升了迭代效率
  • 2B和2C的GenUI需求差异显著 — 前者需要Workflow级别的GenUX

未来方向：Agentic UX

从GenUI到GenUX，再到Agentic UX — AI不仅生成界面，还能代替用户执行任务。设计师的角色正在从"画界面"转变为"定义AI的行为边界和表达框架"。
